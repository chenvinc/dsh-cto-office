# W10 实现记录（M-7 可落地部分：岗位 → 模型/档位）

> 对应方案 §4.7 / §7.2 M-7（「岗位档位」，二期但可先落地一半）。
> 状态：**已实现并强制校验** · 单测 **98/98**（新增 10 例）· E2E **28/28** · 注入 **9/9** · 探针 **0 FAIL**。

## 需求（用户口径，2026-11-26）

> 「cto 这类需要较强思考能力的用 Tencent hy4，工程师这类重在工程执行的用 deepseek v4.1 flash（1017 后缀优先）」

拆开是两件事，插件只能做后一件：

| 谁 | 模型 | 由谁决定 |
|---|---|---|
| **CTO 本体**（会话） | hy4 | **你在模型选择器里选**（插件改不了会话模型） |
| architect / reviewer（强思考） | `magpie/opencode-go/hy4` @ `high` | 插件（岗位表 + 派工校验） |
| builder（工程执行） | `magpie/opencode-zen/deepseek-v4.1-flash` @ `high` | 同上 |
| qa / ux / product（工程执行） | `magpie/opencode-zen/deepseek-v4.1-flash` @ `low` | 同上 |

## 为什么不能「配一下就好」

三层阻碍，逐层查过：

1. **preset 设不了默认档**（W0 ⑥）：preset 行的 `agentOptions` 被 schemastery 保留但无人消费。
2. **子代理模型选择默认关闭**（`subagentModelSelection = { enabled:false, allowedModels:[] }`）：
   一关就只允许「父路由」，任何别的模型都被拒 —— 这正是 W0 ⑤c 的真实来源。
3. **宿主只有两种粒度**：tool 级统一默认（`agentOptions`，所有子代理同一个）或每次派工显式传参。

所以「按岗位分」只能由插件维护一张表，并且**由守卫强制**，而不是在提示词里请 CTO 记得传。

## 实现

### 1) 岗位表（`lib/role-models.js`）

```js
'cto-architect': { provider: 'magpie', model: 'opencode-go/hy4', reasoning_effort: 'high' }
'cto-reviewer':  { provider: 'magpie', model: 'opencode-go/hy4', reasoning_effort: 'high' }
'cto-builder':   { provider: 'magpie', model: 'opencode-zen/deepseek-v4.1-flash', reasoning_effort: 'high' }
'cto-qa':        { provider: 'magpie', model: 'opencode-zen/deepseek-v4.1-flash', reasoning_effort: 'low' }
'cto-ux':        { provider: 'magpie', model: 'opencode-zen/deepseek-v4.1-flash', reasoning_effort: 'low' }
'cto-product':   { provider: 'magpie', model: 'opencode-zen/deepseek-v4.1-flash', reasoning_effort: 'low' }
```

- 配置可覆盖（`roleModels`），也可用 `null` **摘除**某个岗位（= 该岗位不参与校验）。
- 坏配置**连带摘除默认项并报告**：留着默认值会让人误以为配置生效了。

### 2) 派工守卫强制（`lib/guards.js`）

`subagent` 调用先解析岗位（省略 `agent_preset` 按 `cto-builder` 处理，沿用 P1 的 fail-closed 口径），
再按表校验 `provider / model / reasoning_effort`。漏传或传错 → **deny**，拒绝理由里直接给出该传的三个参数
+ 整张岗位表，CTO 不用试错。

放在名额检查**之前**：路由错了的纠错成本比名额问题更低。

### 3) 派工响应带路由（`lib/tools.js`）

`office_dispatch` 的响应（含 QUEUED 两种情形）末尾追加：

```
派工路由（按岗位表，pre-execute 会校验）：cto-architect → magpie/opencode-go/hy4 @ high
```

## 前提（一次性的，已由用户完成）

DSH **设置 → 子代理 → 模型选择** 打开，并勾选路由。本机写入的是 profile 的
`cordis.patch.yml`：

```yaml
- id: subagent-model-selection-settings
  config:
    enabled: true
    allowedModels:
      - { provider: magpie, model: opencode-go/hy4 }
      - { provider: magpie, model: opencode-zen/deepseek-v4.1-flash }
      - { provider: magpie, model: opencode-zen/deepseek-v4.1-flash-free }
```

**授权在会话创建时写进会话策略** —— 设置改完必须**新开会话**才生效；旧会话会一直只允许父路由。

### 顺带用数据回答了「为什么必须新开会话」

同一次复核里对比了会话归档里的 `subagentModelSelectionPolicy`：

| 会话 | 创建时机 | 策略 |
|---|---|---|
| `5f0c8bf6…` / `6f26025a…` | 设置开启**前** | `null`（只允许父路由） |
| `session-b44601b3…` / `915b4da2…` / `459ce36a…` | 开启**后** | 三条 magpie 路由 |

所以本文 §前提 那句「设置改完必须新开会话」不是推测，是磁盘上可查的事实。

### 口径与边界（如实记）

- **省略 `agent_preset` 时按 `cto-builder` 处理**（P1 的 fail-closed 一致），所以路由也按写岗校验 ——
  验收时若要验 hy4，必须显式写 `agent_preset=cto-architect`；只省路由参数、连岗位一起省，拒绝理由里会是 flash。
- 真机只测了 `cto-architect` 一岗；其余五岗由单测覆盖（同一段校验代码，风险低但未逐岗真跑）。
- **传错值**只有单测覆盖（provider/model/effort 三类都测了），真机未跑「传错」这一支。
- 已真机验证「父 provider ≠ 子 provider」的组合成立：父 `dsh-opencode-go`、子 `magpie`。
