## 二、A 类：硬伤（设计漏洞，必须先补）

### A1 · 工件层可见性契约没闭合

**定位**：汇报 03·M4、"一卡一流"架构图（图 3）；方案 §4.2 A 层 + §4.3 2a（L257 目录树）。

**原文依据**

- §4.2 A 层：worker 的 `cwd` 指向 `card/<id>` 的 worktree，D2 明确"两个 worktree 互不可见"。
- §4.3 2a：`.cto-office/` 挂在 `<workspace>` 根，即主检出。
- §4.2 配套：派工前置条件要求"`git status` 除 `.cto-office/` 外无改动"，说明它被当成主检出内的 git 可见目录。

**问题**

两块事实互相矛盾：工件在主检出，worker 在独立 worktree。

1. worker **读不到** CTO 落盘的 `contracts/`、`acceptance/` —— M4 主张的"对照物"在 worker 视野外，M3 自检闸门失去比对对象，退化成凭记忆自查。
2. worker 若照文档往 `.cto-office/receipts/` 写回执，文件实际落在自己分支上：要么被 `office_gate` 判成越界（不在授权清单），要么合并时与主线冲突。

**后果**：M3、M4 两级机制同时悬空；这是本版方案里唯一会**直接导致机制不成立**的漏洞，其余问题都只是成本。

**建议**（三选一，三者可在不同阶段并存）

| 方案 | 做法 | 代价 |
|---|---|---|
| ① 工件走宿主存储 | 用 §3 已列出的 `storageDomain.open(spec)`（durable JSON），不进 git，两边都能读 | 工件不可 review、不可随仓库交接 |
| ② 只读注入 worktree | `office_dispatch` 建 worktree 后把 `contracts/`、`acceptance/` 复制（或软链）进去并 `git exclude`；回执仍由 CTO 在主检出落盘 | 需定义"工件更新后如何重新注入" |
| ③ 工件随分支走 | 工件进分支，合并时才落主检出，需定义合并期工件冲突规则 | 冲突面变大，与 A5 叠加 |

另需在文档里补一句明确结论：**`.cto-office/` 是否进 git**。若进，worktree 创建时带过去的是"已提交版本"，未提交内容不会跟过去（这条现在只写在派工前置条件里，位置不对）；若不进，则"跨检出共享"必须另找通道，②③ 均失效。

**状态**：☐ 待改 ☐ 已改

### A2 · 闸门、自检、走查各在哪个检出跑，未定义

**定位**：汇报 03·M1/M3/M6、05 章阶段 3、06 章；方案 §4.2 A/C 层。

**原文依据**：§4.2 A 层"主检出保持基准态，天然可当验收基准"；但新代码不在主检出。

**问题**：三类检查被统称"通过"，执行的检出位置却不同，导致三个后果：

1. QA 在主检出验收 —— 验收的是**旧代码 + 别人的已合并代码**，不是这张卡。
2. QA 在 worktree 验收 —— 验收环境是分支独有环境（依赖是否已装未定，见 §4.2 实测项 2），结论不可跨卡比较。
3. M6 人工走查若也在 worktree 上做，走查结论随分支删除而消失。

**后果**：M2/M3/M6 的"通过"没有统一定义，同一张卡重复跑可能得到不同结论，06 章的"可复跑"不成立。

**建议**：显式定义三段基准，并在汇报里画出顺序：

| 环节 | 执行位置 | 判据 |
|---|---|---|
| `office_gate` | 检出无关（纯文本比对） | `diff/status` vs 授权清单 |
| `SELF-CHECK` | worktree 内 | 对 `acceptance` 逐条 |
| 人工走查 / 终验 | **合并后**主检出 | 唯一出口，`settle` 前置 |

即"越界判定与检出无关，行为验收只在合并后"。这句话应直接写进 M3 的一句话结论。

**状态**：☐ 待改 ☐ 已改

### A3 · diff 基线 `base` 未定义

**定位**：汇报 03·M2；方案 §4.2 C 层（L229）`git diff --name-status <base>..card/<id>`。

**问题**：`<base>` 全文是占位符。`worktrees.create` 虽然返回 `baseCommit`，但没规定**卡内是否存 sha**。一旦 main 前进（别的卡先合并），`base..card/<id>` 会把已合并的他人变更算进本卡 diff。

**后果**：判定结果随合并顺序漂移 —— 同一张卡重跑得到不同结论，M2"客观可复跑"直接失效，且越界报告会冤枉人。

**建议**：卡 JSON 增 `baseSha`，开卡时冻结；判定固定用 `git diff --name-status <baseSha>..card/<id>`；合并前再补一次"他人是否动过本卡授权路径"的反向检查。

**状态**：☐ 待改 ☐ 已改

### A4 · 回退阈值三处不一致

**定位**：汇报 03·M5 / 05 章 / 06 章；方案 §4.5（L314）。

**现象**

| 出处 | 表述 |
|---|---|
| 03·M5 | 同一张卡第 3 次回退转人 |
| 05 章 | 阈值 2 触发转人 |
| 06 章 | ≥3 次自动转人 |
| 方案 §4.5 | "≥2 次升级" + "第三次回退直接 deny" 混写在同一句 |

**后果**：实现时只能选一个，另两处成为错误说明；状态机与闸门对"第 2 次回退"的行为分歧，测试用例也会写成两套。

**建议**：统一为一句、一个数字 —— "回退计数达 2 即转人，第 3 次直接 deny 且不再派回"；计数落 `cards/<id>.json` 的 `revisions`，由插件写、CTO 只读。四处文案同步改。

**状态**：☐ 待改 ☐ 已改

### A5 · 共享文件双写：D5-6 是反证，不是例证

**定位**：汇报 03·M2、05 章 D5-6；方案 §4.2 C 层、§6 风险表。

**问题**：`shared/types.ts`、路由表这类**必然被多卡改**的文件，当前靠 `ESCALATE` 提权 + 口头同步处理。而 05 章 D5-6 "两人都动了路由表"被当成机制有效的演示，实际上它证明的是：**授权清单本身不预防共享文件双写**，只在你事后才发现。

提权后两张卡都拿到 `rw`，冲突并没有被消解，只是被推迟到 `git merge` 那一刻 —— 也就是最贵的时刻。

**后果**：合并冲突成为主要返工来源，且第一次暴露总在最贵的节点；同时"提权即放行"会让 A5 与 B4（租约）产生循环依赖。

**建议**：清单增加**互斥组** `exclusive: [glob]` —— 同一个 glob 同时只能被一张在飞卡持有，第二张卡在 `office_dispatch` 时直接排队（复用 `blocked_by`），不进入并行。冲突从"合并时"提前到"开卡时"暴露。这一条不改架构、实现成本极低，**建议进一期**（单检出形态下它是唯一能防双写的机制）。

**状态**：☐ 待改 ☐ 已改

### A6 · 阶段 4.7 的岗位档位缺可行性证据

**定位**：汇报 02 章角色、08 章落地路线；方案 §4.7（L326–359）。

**问题**：方案自承现状"全部继承父路由，无法按岗位调档"，而 §4.7 的整张档位表（CTO 抬阈值、worker 更激进压缩、按岗位 `allowedModels`）全部建立在一个**未实测**的宿主能力上：preset 级 model/variant 覆盖。

**后果**：若实测不通过，§4.7 整章作废，排期里"0.5–1 天"的预算变成 0 天收益；更麻烦的是 M1 的成本模型（"CTO 用强模型、worker 用 flash"）会失去一半前提。

**建议**：W0.1 加第三项实测（前两项是沙箱 `workspaceRoot`、worktree 依赖安装）。实测不通过时的降级路径写进文档：全局统一 flash + 只在 CTO 的关键判定点用人确认。别让这张表以"已定"的口气出现在汇报封面。

**状态**：☐ 待改 ☐ 已改

## 三、B 类：过度设计（可直接砍的成本）

### B1 · 外部锚点 CI

**定位**：汇报 07 章四道补丁；方案 §12.4 P4（L609）。

**问题**：需要远端 + CI + 每次合并 push。它防的威胁是"本地测试撒谎"，但单人仓库里撒谎的受益者和受害者是同一个人 —— 没有对手，就没有需要外部锚定的动机。

**建议**：移出本期。降级为"合并后在本地跑一遍并记录输出到 `audit.jsonl`"，保留证据、砍掉链路。等真的出现第二个人写代码时再装。

**状态**：☐ 待改 ☐ 已改

---

### B2 · append-only hash 链审计账本

**定位**：汇报 07 章；方案 §12.4 P3（L608）。

**问题**：hash 链只有在"写账本的人不能改账本"时才有意义。当前插件跑在用户机器上、仓库写权限也在同一人手里 —— 有写权限即可重算整条链，链只防自己。

**建议**：降级为普通 `audit.jsonl`（无 hash 链）。真正有效的那半条保留：**插件写、CTO 只读、文件进 git 可 review**。"能 review"比"能验 hash"更实用。

**状态**：☐ 待改 ☐ 已改

---

### B3 · 插件自校验 fail-closed

**定位**：汇报 07 章"被监管者能不能改监管者"；方案 §12.4（L615）。

**问题**：改插件的人就是装机的人，收益接近 0；而 fail-closed 的实际风险很实在 —— 一次升级后 hash 对不上，整个判定层拒绝启用，**无法自救**（判定层就是你的救援工具）。

**建议**：改为"校验失败 → 大声告警 + 面板常亮 + 不阻塞判定"。告警保留，fail-closed 去掉。

**状态**：☐ 待改 ☐ 已改

---

### B4 · 检查点五项冗余 / receipts 拆分过度 / "租约"未定义

**定位**：汇报 03·M4/M5；方案 §4.3 2a（L257）、§4.4 3c（L305）。

**三个小问题合并为一条**

1. **检查点五项**（阶段、时间、patch sha、任务板快照、工件版本、租约）：阶段与时间、patch sha 三者可互相推导，真正不可重建的只有"任务板快照 + 工件版本 + 在飞卡与 worktree/分支对应关系"。
2. **`receipts/` 独立成目录**：同一张卡的信息被拆到 `cards/` 和 `receipts/` 两个目录，review 一张卡要跳文件夹，反而增加核对成本；`checkpoints/` 与 `audit` 同时存状态，容易互相矛盾且无人仲裁。
3. **"租约"全文未定义**：§4.2 配套、§4.4 表格都用了这个词，但没有字段、没有超时、没有谁能续、过期后卡归谁。

**建议**：`receipts/` 并入 `cards/`（或改 `cards/<id>/` 单目录结构）；检查点精简为四项；租约补一行定义（字段 + 超时 + 续租方 + 过期后处理），否则这个词在实现时一定歧义。

**状态**：☐ 待改 ☐ 已改

## 四、C 类：缺失

### C1 · 卡的粒度没有可机检上限

**定位**：汇报 03·M1 全节（"一卡一流"是整个方案的地基）。

**问题**：全篇没有定义"什么算一张卡"。如果一张卡可以无限大，那么 worktree 隔离、授权清单、闸门都退化成形式 —— 一张巨型卡永远是"授权内"的。

**建议**：给三条硬上限，超限由 `office_dispatch` 拒绝建卡并要求拆卡：

| 维度 | 建议上限 |
|---|---|
| 变更文件数 | ≤ 10 |
| 净变更行数（可用 diff 行数近似"能否一次评审判完"） | ≤ 400 |
| 可观测行为变化 | 恰好 1 个（对应一条 `acceptance`） |

**状态**：☐ 待改 ☐ 已改

---

### C2 · 失效信号只有 1 条孤例，应成体系

**定位**：汇报 06 章"怎么证明有效"；方案 §12.4。

**问题**：目前只有 D5-6 一条（连续三张卡 `gaps` 写"无" → 自检走过场）。孤例的问题不是不成立，而是它只能事后发现，且换一种失效形式就抓不到。

**建议**：补一张信号表（信号 / 采集点 / 阈值 / 反应），至少覆盖：

| 信号 | 为什么是失败信号 |
|---|---|
| 授权清单持续变宽（提权率上升） | 清单在退化成形式 |
| 闸门一次通过率接近 100% | 判据太松，或根本没人看 |
| 回退次数恒为 0 | 要么卡都太小，要么闸门没在拦 |
| 每卡 token / 点数持续上升 | 卡粒度失控 |
| 工件版本长期不变 | M4 没在落盘 |
| 走查记录雷同 | M6 走过场 |

其中**"闸门 100% 通过"和"回退恒 0"必须当失败信号读**，不能当质量指标 —— 这条要写进汇报，否则面板一上线就会被误读成"机制运行良好"。

**状态**：☐ 待改 ☐ 已改

---

### C3 · 成本口径与额度约束耦合不足

**定位**：汇报 08 章、06 章成本；方案 §4.7 上下文额度段（L348）。

**问题**

1. 只记 token，但 token ≠ 额度消耗：不同模型输出单价差 50 倍以上（Kimi K3 约为 MiMo 的 53 倍）。同样 1M token，成本差一个数量级。
2. 额度是按时间窗给的，而并行会**同时**占用窗口。M1 的风险清单里没有这一条，可它比 worktree 依赖安装更早撞墙 —— 开工第一天就会遇到。

**建议**

- 记录三元组「模型 + 档位 + token」，按当前额度基准折算成"点数"，配置与成本表同源。
- M1 风险清单加一条：**"并行对时间窗额度的挤占待实测"**，并给出降级策略（并发上限 / 高峰串行）。

**状态**：☐ 待改 ☐ 已改

### C4 · 封面"待确认 1 项"没指明是哪一项

**定位**：汇报封面（"已定 10 项 · 待确认 1 项"）；方案 §8、§10.4、§11.4、§12.6。

**问题**：全文有四个"待确认 1 点"，封面却只说"1 项"。读者无法定位，也无法在评审时只针对那一项讨论 —— 汇报的目的是"让人拍板"，这一条恰好把拍板对象藏起来了。

**建议**：封面直接写出未定项标题（如"待确认：§11.4 模型分档实测"），或在封面列出全部未定项编号。

**状态**：☐ 待改 ☐ 已改
