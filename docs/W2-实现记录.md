> 对应方案 §4.3 2a/2b/2c + §14.1 + §14.8。
> 状态：**已实现，单测 20/20、E2E 19/19 全绿**。集成到运行宿主待 W0。

## 交付

| 文件 | 作用 |
|---|---|
| `lib/artifacts.js` | 工件层：契约/验收基线、版本号、`artifactsVersion`、进行期禁改 |
| `lib/receipt.js` | 回执协议：解析 `RECEIPT`/`SELF-CHECK`，校验字段、版本、范围、验收条目 |
| `lib/receipt-guard.js` | 挂在 `tools/post-execute`：写岗缺回执 → **block**，要求补齐重交 |
| `lib/tools.js`（扩展） | 新增 `office_artifact`；`office_dispatch` 冻结工件版本、无验收基线不许派工；`office_gate` 判定前先验工件 |

## 五条落地的约束

1. **工件先于卡**：没有 `acceptance` 工件，`office_dispatch` 直接拒绝 —— 没有对照物，闸门无从判起。
2. **版本冻结**：派工时把 `{contracts, acceptance}` 版本写进卡；只冻结**存在**的工件（`contracts` 可选）。
3. **进行期禁改**（M-14）：卡存在且非终止态（含 `QUEUED`）时，`office_artifact.write` 抛 `CARD_IN_PROGRESS`，要求作废重开。
4. **回执必须写读了哪一版**：`artifactsVersion` 与卡不一致 → 打回并说明「你读的是 v1，卡已定稿 v2」—— 返工责任可归因。
5. **缺字段 fail-closed**：回执是判定输入，缺就 block；与「判定器自身失败只告警」不冲突。

## 实现中发现并修正的 2 个语义问题

| # | 问题 | 修正 |
|---|---|---|
| 1 | 工件锁只覆盖 `DISPATCHED`/`CHANGES` | **`QUEUED` 也必须锁**：版本在开卡时就冻结了，排队期改口径同样造成「按 v1 做、按 v2 验」 |
| 2 | `contracts` 被当成必填 | 改为**可选**：小卡没有契约是合理的，但对齐时仍校验版本；`acceptance` 必填 |
