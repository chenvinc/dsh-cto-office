## E2E 覆盖（`npm run e2e`）

1. 派工 → DISPATCHED，冻结 baseSha
2. 第二个写卡 → QUEUED（`serial-limit`）
3. 越界 → CHANGES，且**双读**（diff 抓到已跟踪、status 抓到未跟踪）
4. 闸门未过 → 拒绝结算
5. 工作区干净但闸门非 PASS → 仍拒绝结算
6. 作废 → ABANDONED，释放互斥并解除 QUEUED 阻塞
7. **C2 启动时才冻结 baseSha**（A3），不含此前已合并的他人改动
8. 授权内改动 → PASS → 可结算
9. 重复判定 → 新增一件证据而非覆盖

## 实现中发现的 3 个真问题（只有跑 E2E 才会暴露）

| # | 问题 | 后果 | 修法 |
|---|---|---|---|
| 1 | `baseSha` 在建卡时冻结 | 排在队列里的卡，等期间 main 前进，启动后 `baseSha..HEAD` 把他人改动算成本卡越界（批注 A3 的真实形态） | 冻结时机移到**真正拿到写者名额那一刻**；`office_dispatch` 对 QUEUED 卡二次调用 = 启动 |
| 2 | `release` 只查工作区干净 | **越界改动提交后工作区也干净** → 越界卡能直接结算，闸门形同虚设 | 结算必须校验最新证据 `verdict === 'PASS'`，否则拒绝并提示重跑或作废 |
| 3 | `.cto-office/` 只从 `status` 过滤 | 工件提交后，`diff base..HEAD` 把它算作越界文件 | `diff` 与 `numstat` 同样按前缀过滤 |

> 这三个都不是「写错一行」，而是**判定语义的缺口**。第 2 条尤其危险：它会让「未过闸门不能结算」整条主张失效，而单测全绿时看不出来。

## 能力审计与偏离报告（2026-11-26）

按「有系统能力就不要自己写」审计了三个自写模块：

| 模块 | 系统里有没有 | 结论 | 处理 |
|---|---|---|---|
| glob 匹配 | **有**：宿主自带 `picomatch@4.0.7` | 我确实在重复造轮子 | **已改为薄适配层**：经 `createRequire(DSH_INSTALL_DIR/package.json)` 解析 picomatch，失败才退回内置最小匹配器；`matchBackend()` 自报当前后端 |
| 原子写 | **有**，但**不满足需求**：`@deepseek-ai/dsh-atomic-write` 源码写明「Crash durability (fsync) is out of scope」，并留有 `TODO(settings-atomic-durability)` | 它是「原子可见」，不是「崩溃持久」；而 M-2 要处理的正是崩溃 | **保留自实现**（temp→fsync→rename→dir-fsync），并在依赖清单记为偏离；上游补齐后可删约 40 行 |
| 定时器 | **有**：`ctx.timer.interval`（`cordis-plugin-timer`） | 不该自建 | **已改用** `ctx.timer`；探测不到时明确跳过，不改用 `setInterval` 偷跑 |
