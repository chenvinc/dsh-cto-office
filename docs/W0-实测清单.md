### 发现 1 · 输出 schema 必须是标准 JSON Schema 方言

首次安装报错（宿主 diagnostic 原文）：

```
cto-office-live (@swiper1881/dsh-cto-office): JsonSchemaError: unsupported JSON schema:
  schema.properties.cardId.required is not supported on type "string";
  schema.properties.blockedBy.required must be an array of strings; ...
```

**原因**：`parameters` 用的是 DSH 简化方言（属性上写 `required: true`），
但 `output.schema` 走**标准 JSON Schema** —— `required` 必须是对象层的字符串数组。

**修复**：`jsonSchemaOf(properties, required)` 统一把 `required` 提到对象层；
并加单测断言「属性上不得出现 `required`」，防止再犯。

### 发现 2 · 未声明 inject 就读服务属性会抛错

第二次报错：

```
cto-office-live (@swiper1881/dsh-cto-office): Error: cannot get property "timer" without inject
```

**原因**：`inject = ['tools']`，但代码里读了 `ctx.timer`。cordis 对未 inject 的服务属性
访问直接抛错（不是返回 undefined）。

**修复**：`try { timer = ctx.timer } catch { timer = undefined }`；
并加「严格 ctx」回归测试（Proxy 模拟 cordis 抛错）覆盖 `timer / agentPresets /
workingDirectory / sandboxPolicy` 四个可能的裸读点。

> 这两条都**只有装进真宿主才会暴露**：Node 单测里我用的是 fake ctx 与自造 schema，
> 假对象不会拒绝任何东西。这就是 W0 的价值。

# 追加：真机第一轮反馈（CTO 会话实测）与修复

> 来源：在本工作区开「CTO 办公室」会话后的一次实测（实际生效预设为 `standard`，
> 详见反馈原文）。四条反馈**全部成立**，均已修复并加回归测试。

## 发现 3 · 工具越权：`when` 收窄 fail-open（最严重）

| 项 | 内容 |
|---|---|
| 现象 | `standard` 会话与 worker 子会话都能看到并调用 6 个 `office_*` |
| 根因 | 全局 host 半用 `ctx.agentPresets.presetForSession` 做 `when` 收窄；cordis 对未 inject 的服务属性**抛错**，而 `inject` 没有「可选」语义 → catch 成 `undefined` → `when` 恒 true |
| 我的单测为何没抓到 | 我写的断言是「apply 不抛」，恰恰证明了这条 fail-open 路径 |
| 修复 | 不再运行时收窄：新增 `tools-plugin.js`，把工具与守卫挂进 **`cto-office` 预设自己的 plugins**（patch 里 `office-tools` 行）。隔离由组装层负责 |
| 验证 | 修复后 `standard` 会话工具列表 41 个，`office_*` 出现 **0 次** |

> 这条印证了设计原话：「能力层剥夺优于运行时判定」。我最初用 `when` 是偷懒。

## 发现 4 · 参数方言：标准 JSON Schema 才被识别

| 项 | 内容 |
|---|---|
| 现象 | `include` / `acceptance` 落盘成 `"[\"…\"]"` 字符串；`declared.files` 变 `"1"`；`behaviors` 变字符串长度 87 |
| 根因 | `ToolSchema.parameters` 是**标准 JSON Schema**；我按作者声明方言写了属性级 `required: true`，宿主不校验、静默放行 |
| 修复 | `lib/args.js`：`toStandardSchema()` 转换 + `coerceArgs()` 强校验。字符串化的数组/整数**显式归一并在 message 留痕**；非法类型直接报错带期望类型 |
| 附带 | `workspace` 改为 schema 必填；`subject`/`mode` 改为可选（只启动已存在 QUEUED 卡时可省），改由代码按路径校验 |

## 发现 5 · 回执闸门挂点错误

| 项 | 内容 |
|---|---|
| 现象 | ① 派工失败时闸门仍运行并**吞掉真实报错**；② 正常派工只在「started subagent X」上判缺回执 → 每次写岗派工都会被 block；③ worker 真正回执永远不记账 |
| 根因 | `subagent` 工具**立即**返回受理回执；worker 最终答案走**完成通知**，不经过 `tools/post-execute` |
| 修复 | 闸门：先判 `result.isError` 放行（保住真实报错）；**只在文本确有 `RECEIPT:` 时才校验**。新增 `lib/receipt-collector.js` 监听 `session/event`，从完成通知里捡回执并记账 |
| **如实报告** | 完成通知已落库，**无法在此打回**；自动打回需要能拦住完成通知的钩子，当前宿主没有。缺回执由 `office_gate` 的 `receipt-missing` 兜住 —— 这是可靠的那道 |

## 发现 6 · 死代码

`index.js` 里 `ctx.set?.('ctoOffice', { store })` 的 `store` 在重构后已不存在，ReferenceError 被 try/catch 静默吞掉。随 host 半简化一并移除。

# 追加二：真机第二轮（CTO 预设闭环跑通）与 P0 修复

> 来源：在真 CTO 预设会话里跑通「工件 → 开卡 → 派工 → 回执 → 闸门 → 结算」整链，
> 产物提交 `c0450f1`（README +18 行）。**链路成立且 fail-closed**：
> `changed` 少写文件、`artifactsVersion` 读错版本、自述冒充结论，都会被 gate/settle 卡住。
> 但暴露了一个 P0 缺陷。

## 发现 7 · P0「开卡即自锁」

| 项 | 内容 |
|---|---|
| 现象 | `office_dispatch` 占名额（卡 → DISPATCHED）后，紧接着派 `cto-builder` **必被自家守卫拒**：「写者名额已满：C2 正在写」→ 单卡永远开不了工 |
| 根因 | 守卫只数「名额是否已满」，**不看派工 prompt 里的【任务卡 X】是否就是持锁那张卡**。`cardIdFromPrompt` 已在回执侧落地，守卫侧没接 |
| 修复 | 守卫先解析 prompt 里的卡号：<br>· 命中的卡正是持锁卡 → **放行**（这是它自己的派工）<br>· 命中的卡是 QUEUED → 拒绝并提示「先 `office_dispatch` 启动它」<br>· 没写卡号或写了别的卡 → 按名额拒绝，并明确提示补 `【任务卡 X】` |

## 发现 8 · P1「省略 `agent_preset` 即绕过两道守卫」

宿主 `subagent` 的默认 preset 就是 `cto-builder`（patch 的 `delegation.agentPreset`），
不写 `agent_preset` 时默认派的就是写岗。而两道守卫都只看「声明的 preset」——
**少写一个参数就能同时绕过名额守卫与回执守卫**。

修复：`targetPreset()` 在未声明时回落到 `config.defaultAgentPreset`（默认 `cto-builder`），
即**按写岗处理（fail-closed）**。只读岗必须显式声明 preset 才享受豁免。

## 发现 9 · P3 同一份回执被记两条证据

采集器在 `assistant/message` 与完成通知两条事件上都会命中同一段文本。

修复：按内容摘要去重（`changed` 排序集合 + 验收条目 + 版本），写入 `card.lastReceiptDigest`，
相同内容不再记账。判定不受影响（本来就取最新权威证据），但证据条数不再虚高。

## 发现 10 · 闸门自己抓到的 P0 误判：非 ASCII 路径

C3 改的是 `docs/W0-实测清单.md`（中文名，内容与授权都正确），却被判 CHANGES：

```
- [out-of-scope]      "docs/W0-\345\256\236..." — 不在授权清单内
- [receipt-overclaim] docs/W0-实测清单.md       — 回执声称改了，git 里没有
- [receipt-underclaim] "docs/W0-\345..."        — git 显示改了，回执没声明
```

根因：`git` 默认 `core.quotePath=true`，把非 ASCII 路径转义成八进制字面量。
**任何中文文件名都会踩**——C2 只改 `README.md` 所以没暴露。

修法（已由 C4 落地）：`-c core.quotePath=false`，并加「剥掉 `-c` 断言必红」的反证用例，
确保这条回归测试有牙齿。

## 发现 11 · glob 主路径在真机没生效（`backend = fallback`）

`office_status` 报 `glob 后端 = fallback`。根因：解析锚点只用了 `process.env.DSH_INSTALL_DIR`，
而该变量**只存在于 bash 工具的环境**，桌面版 Host 进程里没有 → `MODULE_NOT_FOUND` → 一直跑内置兜底。

修法：
- 锚点改为**多路探测**：`DSH_CTO_OFFICE_PICOMATCH` → `DSH_INSTALL_DIR` → `process.resourcesPath`
  （`app.asar/dsh`、`dsh`、`app` 三种布局）→ 由 `process.execPath` 反推 → 本包自身位置；
- 命中后校验 `typeof fn === 'function'` 且行为正确才采用；
- `matchBackend()` 之外新增 `matchBackendAnchor()`，`office_status` **直接显示命中的锚点**，
  未生效时打 ⚠ —— 这样「设计上的主路径是否真的生效」以后可一眼核对。

**本机验证**（Electron 运行时、去掉 `DSH_INSTALL_DIR`）：
```
resourcesPath = /Applications/DeepSeek Harness.app/Contents/Resources
backend = picomatch
anchor  = /Applications/DeepSeek Harness.app/Contents/Resources/app.asar/dsh/package.json
```

## 发现 12 · `\t` 解析脆（CTO 建议开卡，已一并修）

`diff --name-status` / `status --porcelain` / `diff --numstat` 原先按 `\t` / 换行切分，
文件名含制表符就错位。改为 **`-z`（NUL 分隔）** 解析，并对重命名/复制的双路径格式单独处理。

## 发现 13 · 去重摘要过粗（CTO 反馈 ⑤，已修）

原摘要只含结构（changed 集合 + 验收结论 + 版本），builder 与 reviewer 的回执结构相同时会被误判为重复，
导致证据条数偏低。摘要改为 **sha256(结构 + 正文指纹)**。

附带事实（补一条理解）：该锚点位于 **asar 归档内部**，shell 进不去——`ls: … /app.asar/dsh: Not a directory`。能解析它的是宿主 Electron 的 Node fs。这正好解释了为什么「用 bash 工具环境验证」会得出 `fallback` 的错误结论（发现 11 的根因同源）。

### ④ 跨检出只读 — PASS，但**原测法测不出东西**（重点）

原测法「worker 只读主检出的 `.cto-office/`」在一期**必然通过**：一期 worker 与主检出同目录，不存在跨目录读。二期 worktree 在 workspace **之外**，所以真正要问的是**沙箱允不允许读工作区外的路径**。

改法：把 C2 的 `card.json` 复制到 `/tmp/cto-outside-probe/`（工作区外），让 worker 同时读主检出路径与此路径。

结果（architect 原话）：「两个路径都读取成功」，`cardId` 都是 `C2`；路径 2 解析为 `/private/tmp/cto-outside-probe/card.json`，**无任何报错**。子会话沙箱档位 `workspace-write`（源自 `delegation`）。

结论：`workspace-write` 下**读**不受工作区边界限制 → **二期 worktree 从主检出 `.cto-office/` 取工件没有沙箱障碍**。按原文档红线，一期工件层**不做**任何降级。

### ⑤ 档位：三小步，结论写死

**5a · 只传档位 → 报错，不回退**（原清单「看是否被拒或回退到父路由」的答案是「被拒」）：

```
Error: child LLM `reasoning_effort` requires both `provider` and `model`; supply both or omit all three fields
```

**5b · 完整路由 + `low` → 成功，且 `low` 真生效**：

子代理本身读不到自己的 model/effort（宿主未把它注入环境变量或会话元数据），取证改看归档。**已独立复核**：子会话归档 `~/.dsh/sessions/…/53de8d80…/session.v4.jsonl.zstd` 的 `request/header` 记录

```json
{"provider":"dsh-opencode-go","model":"deepseek-v4.1-flash","reasoningEffort":"low","maxTokens":65536}
```

→ 档位**真透传到请求层**，不是「接受了但没生效」。

**5c · 非白名单 model → 被拒，但拦截来源不是 `allowedModels`**：

```
Error: child LLM route "dsh-opencode-go/deepseek-v4-pro" is not allowed for this Session;
without a recorded model-selection policy, explicit selection is limited to the parent route
```

拦截来自「**本会话没有记录 model-selection 策略 → 显式选择限于父路由**」。**已独立复核**：本包代码与 `cordis.patch.yml` 里 `allowedModels` / `agentOptions` **零命中**（仅 `docs/` 提到）→ 方案 §4.6 第④项「预置 `allowedModels` 白名单」**仍是未实现的待办**。

档位现状（已用 `list_subagent_models` 复核）：`dsh-opencode-go` 下只有 `deepseek-v4.1-flash` 一个 model，档位 `low` / `high` / `max`。所以 5c 没有「第二个合法 model」可做对照，只能拿不存在的 id 试 —— 错误文案与预期不同，属测具限制，不是结论变化。

> **结论（写死）**：二期的「岗位档位」只能兑现成「**每次派工显式传完整 `provider` + `model` + `reasoning_effort`**」，不能只传档位。若将来想让 CTO「只传档位」，必须先补 `allowedModels` 白名单（未实现），否则 5a 那类报错会直接打断派工。

### ⑥ preset 设默认档 — 不支持

源码：preset 行的 Config 只解析 `id / name / description / order / plugins`；注册时只读 `id` 与 `plugins`。schemastery 对未知字段**保留且不报错**（**已实测**：把带 `agentOptions` 的配置喂给宿主 schema，输出里 `agentOptions` 原样存在，但**没有任何消费方**）→ patch 里写 `agentOptions.reasoning_effort` 是**静默无效**。

本轮**未**改 `cordis.patch.yml`、未重载（改了也测不出东西，且重载有风险）。CTO 会话声明「同意源码结论」，并说明它复核的是「patch 里无任何代码或配置消费默认档」这一层，**未**在 asar 内独立复核 schema —— 如实记录这个边界。

替代路径（**另开卡**）：在目标 preset 的 `plugins` 里挂 `@deepseek-ai/dsh-agent-default-model`（Config **必填** `provider` + `model`，可选 `reasoningEffort`）。但该服务是否作用到会话本体未验证，且会把 provider/model **钉死** —— 与既定的「只做岗位档位、不按模型分档」策略有张力，**需先拍板**。

# 追加五：重载方式纠正 —— `set_bundle false → true` 在 rc.5 下**不会**热重载

> 2026-11-26，DSH `0.2.2-rc.5`，`@swiper1881/dsh-cto-office@0.3.0-alpha.1`（`link:` 安装）。
> 这条纠正的是本文档「三、另外两条真机行为」第 1 条：**那条在 rc.5 上已经不成立。**

实测（两次调用，原文）：

```json
{"stage":"enable","target":"@swiper1881/dsh-cto-office","enabled":false,"changed":true,
 "application":"restart-required","warnings":[],
 "restartReason":"unmanaged-plugin",
 "nextStep":"Tell the user to restart DSH to apply this change: the change reaches a plugin running outside the plugin list."}
```

`enabled: true` 的那次返回完全相同（`restart-required`）。也就是说：

| 项 | 结论 |
|---|---|
| profile 里开关是否变化 | **会变**（`enabled` 真被写进去了） |
| 运行中的宿主是否重新加载模块 | **不会** —— 要重启 DSH 应用 |
| 原因 | `unmanaged-plugin`：该 bundle 的行运行在「插件列表之外」，管理器管不到热切换 |

**对迭代方式的修正**：改 `index.js` / `lib/` 之后，**必须重启 DSH 应用**（退出后重开）才生效；
`set_bundle` 那一步只负责改 profile 里的开关，不负责重新加载代码。以前记的「省一次重装」仍然成立
（不用卸载重装），但「不用重启」这句是错的。

> 推论：任何「改完插件、立刻在会话里验」的动作，都要先把「重启」算进回路。
> 这也解释了为什么 M-2 / M-14 / M-8 三个包在 Node 侧全绿之后，真机验证仍然欠着一次重启。
