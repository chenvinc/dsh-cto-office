### 发现 1 · 输出 schema 必须是标准 JSON Schema 方言

首次安装报错（宿主 diagnostic 原文）：

```
cto-office-live (@swiper1881/dsh-cto-office): JsonSchemaError: unsupported JSON schema:
  schema.properties.cardId.required is not supported on type "string";
  schema.properties.blockedBy.required must be an array of strings; ...
```

**原因**：`parameters` 用的是 DSH 简化方言（属性上写 `required: true`），
但 `output.schema` 走**标准 JSON Schema** —— `required` 必须是对象层的字符串数组。

**修复**：`jsonSchemaOf(properties, required)` 统一把 `required` 提到对象层；
并加单测断言「属性上不得出现 `required`」，防止再犯。

### 发现 2 · 未声明 inject 就读服务属性会抛错

第二次报错：

```
cto-office-live (@swiper1881/dsh-cto-office): Error: cannot get property "timer" without inject
```

**原因**：`inject = ['tools']`，但代码里读了 `ctx.timer`。cordis 对未 inject 的服务属性
访问直接抛错（不是返回 undefined）。

**修复**：`try { timer = ctx.timer } catch { timer = undefined }`；
并加「严格 ctx」回归测试（Proxy 模拟 cordis 抛错）覆盖 `timer / agentPresets /
workingDirectory / sandboxPolicy` 四个可能的裸读点。

> 这两条都**只有装进真宿主才会暴露**：Node 单测里我用的是 fake ctx 与自造 schema，
> 假对象不会拒绝任何东西。这就是 W0 的价值。

# 追加：真机第一轮反馈（CTO 会话实测）与修复

> 来源：在本工作区开「CTO 办公室」会话后的一次实测（实际生效预设为 `standard`，
> 详见反馈原文）。四条反馈**全部成立**，均已修复并加回归测试。

## 发现 3 · 工具越权：`when` 收窄 fail-open（最严重）

| 项 | 内容 |
|---|---|
| 现象 | `standard` 会话与 worker 子会话都能看到并调用 6 个 `office_*` |
| 根因 | 全局 host 半用 `ctx.agentPresets.presetForSession` 做 `when` 收窄；cordis 对未 inject 的服务属性**抛错**，而 `inject` 没有「可选」语义 → catch 成 `undefined` → `when` 恒 true |
| 我的单测为何没抓到 | 我写的断言是「apply 不抛」，恰恰证明了这条 fail-open 路径 |
| 修复 | 不再运行时收窄：新增 `tools-plugin.js`，把工具与守卫挂进 **`cto-office` 预设自己的 plugins**（patch 里 `office-tools` 行）。隔离由组装层负责 |
| 验证 | 修复后 `standard` 会话工具列表 41 个，`office_*` 出现 **0 次** |

> 这条印证了设计原话：「能力层剥夺优于运行时判定」。我最初用 `when` 是偷懒。

## 发现 4 · 参数方言：标准 JSON Schema 才被识别

| 项 | 内容 |
|---|---|
| 现象 | `include` / `acceptance` 落盘成 `"[\"…\"]"` 字符串；`declared.files` 变 `"1"`；`behaviors` 变字符串长度 87 |
| 根因 | `ToolSchema.parameters` 是**标准 JSON Schema**；我按作者声明方言写了属性级 `required: true`，宿主不校验、静默放行 |
| 修复 | `lib/args.js`：`toStandardSchema()` 转换 + `coerceArgs()` 强校验。字符串化的数组/整数**显式归一并在 message 留痕**；非法类型直接报错带期望类型 |
| 附带 | `workspace` 改为 schema 必填；`subject`/`mode` 改为可选（只启动已存在 QUEUED 卡时可省），改由代码按路径校验 |

## 发现 5 · 回执闸门挂点错误

| 项 | 内容 |
|---|---|
| 现象 | ① 派工失败时闸门仍运行并**吞掉真实报错**；② 正常派工只在「started subagent X」上判缺回执 → 每次写岗派工都会被 block；③ worker 真正回执永远不记账 |
| 根因 | `subagent` 工具**立即**返回受理回执；worker 最终答案走**完成通知**，不经过 `tools/post-execute` |
| 修复 | 闸门：先判 `result.isError` 放行（保住真实报错）；**只在文本确有 `RECEIPT:` 时才校验**。新增 `lib/receipt-collector.js` 监听 `session/event`，从完成通知里捡回执并记账 |
| **如实报告** | 完成通知已落库，**无法在此打回**；自动打回需要能拦住完成通知的钩子，当前宿主没有。缺回执由 `office_gate` 的 `receipt-missing` 兜住 —— 这是可靠的那道 |

## 发现 6 · 死代码

`index.js` 里 `ctx.set?.('ctoOffice', { store })` 的 `store` 在重构后已不存在，ReferenceError 被 try/catch 静默吞掉。随 host 半简化一并移除。
