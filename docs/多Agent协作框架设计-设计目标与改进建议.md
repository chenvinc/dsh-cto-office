# 多 Agent 协作框架设计：目标、现状差距与修改建议

> 面向个人开发者的多 Agent 协作框架设计方案。本文只讨论设计层面的机制与边界，不涉及代码或文件级改动。

---

# 第一章 设计目标

## 1.1 核心主张：支持多角色，不支持多写者

框架的定位是一句话：**允许多个角色存在，但不允许多个写者同时动手。**

- **多角色**：架构师、后端、前端、数据库与基础设施、评审、QA、UI/UX 等职责由不同 Agent 承担，各带专业能力与专属 skill。
- **单写者**：同一时刻只有一个 Agent 对代码库执行写操作。并行只在**只读审查**这一层放开——多方同时读、同时评，但不落笔。

这条主张不是保守选择，而是被外部实践反复验证的边界。理由见 1.3 节。

## 1.2 六项设计目标

| 序号 | 设计目标 | 解决的问题 | 关键约束 |
|------|---------|-----------|---------|
| G1 | **三层架构**：Supervisor-Worker + Reflection Loop + Human-in-the-loop | 任务拆解、执行、质检、验收各归其位，避免单点包办 | Reflection Loop 必须有回退机制；Human 关口不可省略 |
| G2 | **单一 Orchestrator**：Supervisor 与 Planner 职责合并 | 拆解者与把关者分离容易互相推诿，信息在两层间损耗 | 合并后需具备跨领域基础判断力，否则退化为纯调度器 |
| G3 | **Worker 职责分工 + 复用社区 skill** | 一人全栈时专业深度不足，重复造轮子 | 按后端、前端、数据库与基础设施三分；skill 只复用经社区验证的 |
| G4 | **两层质量审查**：Worker 轻量自检 + Supervisor 深度审查 | 仅有单层审查时，低级错误污染深度审查带宽 | 自检不授予验收权，"做的人不验收"原则不变 |
| G5 | **UI/UX 覆盖两个端点**：执行前定标 + 执行后对照检查 | 只在开头给设计、结尾凭感觉评价，中间无锚点 | 定标产物必须可对照、可量化 |
| G6 | **纪律写进架构而非提示词** | 靠提示词约束的行为在长链路中必然衰减 | 四层落地：能力层剥夺、流程层状态机、状态持久化、人工关口 |

### G1：三层架构

- **Supervisor**：接收人类任务、拆解、派工、汇总、审查。
- **Worker**：按指派完成具体交付，产出经自检后提交。
- **Reflection Loop**：Worker 提交前执行轻量自检，失败则原地修正；连续失败达阈值必须升级给 Supervisor 而非无限重试。
- **Human**：需求确认、关键节点审批、最终验收。

### G2：单一 Orchestrator

Supervisor（管质量）与 Planner（管拆解）合并为同一主体。合并后同一主体既掌握全局视角又持有细节上下文，消除两层之间的信息损耗与"谁拍板"的争议。代价是对 Orchestrator 的判断力要求提高，需能覆盖后端、前端、数据与基础设施的基本判断。

### G3：Worker 分工与 skill 复用

| Worker 角色 | 职责范围 | 可复用的社区 skill（示例来源） |
|------------|---------|---------------------------|
| 后端 | 接口设计与实现、业务逻辑、服务间通信、性能 | superpowers、addyosmani/agent-skills |
| 前端 | 组件开发、状态管理、路由、样式适配 | ponytail、google/skills |
| 数据库与基础设施 | 数据建模、迁移、容器编排、持续集成与交付 | mattpocock/skills、superpowers |

分工的意义不在于"多开几个 Agent"，而在于**让每类工作的判断标准由具备对应知识的主体执行**，同时用成熟的社区 skill 补齐个人开发者在专业规范上的盲区。

### G4：两层质量审查

| 层次 | 时机 | 覆盖范围 | 权限 |
|------|------|---------|------|
| Worker 轻量自检 | 每次提交前 | 语法、依赖、明显边界错误、基础用例 | 只能要求修正，不能放行 |
| Supervisor 深度审查 | 自检通过后、人工验收前 | 架构合理性、安全、性能、耦合度、跨模块一致 | 可拒绝放行并要求重构 |

分层的核心价值是**保护深度审查的带宽**：确定性、低成本的检查交给机器固定规则，需要推理和领域知识的判断留给 Supervisor。

### G5：UI/UX 两端覆盖

- **执行前定标**：产出可对照的设计规范与验收基线（交互一致性、无障碍、加载体验阈值、度量指标），作为后续可被引用的实体。
- **执行后对照检查**：按同一份定标逐项核验并量化打分，而不是笼统评价"好不好看"。

两个端点用**同一份对照物**连接，中间环节不需要反复口头转述。

### G6：纪律写进架构的四层落地

| 层 | 机制 | 效果 |
|----|------|------|
| 能力层 | 工具不挂载即能力不存在（剥夺而非劝阻） | 越权操作在物理上无法执行 |
| 流程层 | 状态机约束阶段跃迁，非法迁移直接拒绝 | 无法跳过必要步骤，无法乱序调度 |
| 状态层 | 检查点持久化，支持回滚与差异对比 | 中断可恢复、变更可审计 |
| 人工层 | 事前确认、事中抽查、事后验收 | 方向偏离能被及时发现 |

提示词约束的是"意愿"，架构约束的是"可能性"。前者在长链路、多轮转述中必然衰减，后者不会。

## 1.3 外部证据划定的适用边界

三条外部证据共同解释了为什么"多角色 + 单写者"是当前技术条件下的合理边界，而非设计上的偷懒。

| 证据来源 | 关键事实 | 对本框架的含义 |
|---------|---------|--------------|
| Anthropic 的实践反例 | 多 Agent 并行写代码时，协调成本与冲突处理开销会抵消并行收益，甚至引入难以定位的错误 | 写入并行不是免费的加速，而是新增一类故障源 |
| Stanford + SAP CooperBench | 多 Agent 协作在跨模块任务上的成功率从单 Agent 的 **50% 降至 25%** | 跨模块并行写入是成功率腰斩的主要触发场景，必须回避 |
| Cognition 的设计立场 | **写入单线程，额外 Agent 只贡献智力** | 明确给出分工边界：多 Agent 的价值在"想"，不在"写" |

**由此界定的边界**：

1. 并行只在**只读活动**（审查、分析、方案对比）中放开，因为只读不存在写冲突，协调成本可忽略。
2. 写入必须**串行**，同一时刻唯一写者对代码库负责。
3. 额外 Agent 的定位是**智力贡献者**——提供评审意见、发现风险、补充视角，而非共同落笔。
4. 任何"两个写者同时动不同模块"的设计都属于越界，需要显式降级为串行。

# 第二章 cto-office 插件现状与目标的差距

## 2.1 现状描述

分析对象：`@swiper1881/dsh-cto-office@0.2.4`。

| 维度 | 现状 |
|------|------|
| 拓扑 | 单一 CTO 作为唯一 hub 的**星型结构**，所有信息流必须经过中心 |
| 岗位 | 六个：架构师、工程师、评审、QA、UI/UX、业务 |
| 派工链路 | 七条预设链路，覆盖常见任务类型 |
| 流程 | 六步：澄清 → 开卡 → 派工 → 跟进 → 闸门 → 结算 |
| 纪律 | 七条铁律 |
| 岗位关系 | **岗位之间零连线**，不存在横向直连 |
| 权限集中度 | ask-user 与 subagent 派工权限**只在根节点**（CTO） |

这套结构在拓扑层面已经非常接近目标架构：星型天然消除了岗位间的横向信道，权限只在根节点意味着没有权限扩散路径。

## 2.2 逐项对照结论

| 设计目标 | 现状 | 判定 | 差距说明 |
|---------|------|------|---------|
| G1 三层架构 | 有 Supervisor 层，Reflection Loop 带回退（≥2 次失败升级），有人工闸门 | **基本达标** | 缺 Worker 自检这一环，Reflection Loop 实际承担了超出设计的职责 |
| G2 单一 Orchestrator | 单一 CTO 作为唯一 hub | **已达标** | 拆解与把关天然集中在同一主体 |
| G3 Worker 分工 | 六个岗位职责分离，派工链路预设 | **基本达标** | 分工存在，但工程三角色的边界与 skill 复用策略未成体系 |
| G3 能力层硬边界 | 用"工具不挂载"实现能力剥夺 | **已达标** | 越权在物理上不可行，优于任何提示词约束 |
| G3 禁止 fork | 明令禁止 fork 防止权限膨胀 | **已达标** | 与"权限只在根"一致，切断扩散路径 |
| G4 两层审查 | 只有一层审查（评审岗） | **缺口 ①** | Worker 完全无自检，所有错误直扑深度审查 |
| G5 UI/UX 两端 | 只有执行前的设计环节 | **缺口 ②** | 执行后"好不好看"无角色归属，且评审明确排除视觉判断 |
| G4/G5 对照物 | 契约与设计规格不落盘 | **缺口 ③** | 审查失去对照物，只能靠长链路文本转述，信息必然漂移 |
| G6 状态机与持久化 | 六步流程是**文档描述**，非强制状态机；无检查点 | **缺口 ④** | 流程可被绕过，中断不可恢复，变更不可追溯 |
| 单写者原则 | 跨模块场景允许两个工程师并行写 | **风险 ⑤** | `write_scopes` 自承"是提示不是锁" |

### 2.3 已达标部分（五项）

1. **星型拓扑零横向连线** — 岗位之间没有直接信道，所有协作必须经过 CTO 中转。这让"协调"变成中心的可控行为，而不是岗位间的自发行为，从根本上避免了协调成本的指数级增长。
2. **单一 Orchestrator** — CTO 同时承担拆解与把关，消除了两层之间的信息损耗与责任推诿。
3. **Reflection Loop 带回退** — 失败回退并设 ≥2 次升级阈值，避免无限重试吞噬资源。
4. **能力层用工具不挂载做硬边界** — 这是最难被绕过的一层。不挂载即不存在，越权在物理层面无法发生。
5. **禁止 fork 防权限膨胀** — 切断权限沿派生路径扩散的可能，与"权限只在根"形成闭环。

### 2.4 四处缺口（按影响排序）

**缺口 ①：Worker 完全无自检，只有一层审查**

所有产出未经任何过滤直达评审岗。后果是评审岗被低级问题占满带宽，深度审查（架构、安全、耦合）反而没有足够精力。这与 G4"分层保护深度审查带宽"的设计直接冲突。

**缺口 ②：UI/UX 只有执行前设计，执行后无归属**

执行前有设计输出，执行后"好不好看"没有明确角色负责，而评审岗又明确排除视觉判断。结果是视觉质量处于**无人区**——既没有定标后的对照检查，也没有人有权判定不合格。这与 G5"两端覆盖"的要求存在单端缺失。

**缺口 ③：契约与设计规格不落盘，审查失去对照物**

接口契约与设计规格只存在于对话上下文中，不形成持久化实体。审查时只能依赖长链路文本转述，每一跳都可能产生语义漂移。这直接摧毁了 G4/G5 的"对照"前提——没有可对照的实体，审查退化为印象判断。

**缺口 ④：无状态持久化与 checkpoint，流程非强制**

六步流程（澄清→开卡→派工→跟进→闸门→结算）以文档形式描述，不是强制状态机。这意味着流程可被跳过、阶段可被乱序、中断后无法恢复、变更无法追溯。G6 的流程层与状态层均未落地。

### 2.5 一处风险

**风险 ⑤：跨模块场景允许两个工程师并行写**

`write_scopes` 机制自承"**是提示不是锁**"。这意味着并行写入的安全性建立在 Agent 遵守提示的前提上，而非架构约束。一旦两个写者的作用域发生实际重叠，冲突处理与错误定位的成本会显著上升。

这正是 CooperBench 中成功率从 50% 腰斩至 25% 的典型场景。该风险与核心主张"不支持多写者"正面冲突，是当前设计中优先级最高的修正项。

## 2.6 差距总结

| 类别 | 数量 | 具体项 |
|------|------|-------|
| 已达标 | 5 | 星型零横连、单一 Orchestrator、Reflection 回退、能力层硬边界、禁止 fork |
| 缺口 | 4 | Worker 无自检、UI/UX 执行后无归属、对照物不落盘、无状态机与检查点 |
| 风险 | 1 | 跨模块并行写（提示非锁） |

**结构层面的好消息**：五项已达标项集中在**架构骨架**（拓扑、权限、边界）上，这些是最难后期补救的部分。四处缺口集中在**流程执行细节**（自检、对照物、状态化）上，属于可在现有骨架上增量补齐的部分。风险 ⑤ 只需把并行降级为串行即可消除，不涉及结构性改造。

# 第三章 修改建议

以下六条均为设计层面的机制建议，不涉及代码或配置改动。每条给出理由与对个人开发者的成本影响。

## 建议一：写者收敛为单线程，并行只保留在只读审查

**机制**：取消跨模块并行写的许可。同一时刻只允许一个写者持有写权限；需要多视角时，让其余 Agent 以只读方式参与审查、方案比对与风险识别。

**理由**：这是核心主张的直接落地，也是风险 ⑤ 的唯一根治方式。`write_scopes` 作为提示无法提供保证，只有把"同时只能有一个写者"变成架构约束才有效。CooperBench 的 50%→25% 数据说明这不是理论担忧。Cognition 的立场同样明确：写入单线程，额外 Agent 只贡献智力。

**成本影响**：短期看似乎放弃了并行加速，但个人开发者场景下单人本就无法真正并行消费多路写入结果，协调与冲突处理的隐性开销远大于表面收益。实际成本是**负的**——省下的是调试冲突的时间。

## 建议二：补一层 Worker 自检，但不破坏"做的人不验收"

**机制**：Worker 在提交前执行轻量自检（语法、依赖、边界条件、基础用例），自检结果随产出一起提交。自检**只具备要求修正的权力，不具备放行权力**，最终放行权仍在 Supervisor 与人工。

**理由**：缺口 ① 的根源不是"缺少审查"，而是"审查带宽被低级问题占用"。加一层低成本过滤能显著提升深度审查的有效性。同时必须守住权责分离：**做的人不能验收自己的活**，否则自检会退化为走过场。

**成本影响**：每个 Worker 的产出周期增加一次自检耗时（分钟级），换取 Supervisor 审查效率提升。对个人开发者而言，这是投入产出比最高的一条改动——规则确定、无需额外判断力。

## 建议三：让设计规格与接口契约成为持久化对照物

**机制**：接口契约、设计规格、验收基线在产出后落为**可被后续引用的实体**，而非仅存在于对话上下文中。后段审查与验收都必须以这份实体为对照依据，转述不再是信息传递的主渠道。

**理由**：缺口 ③ 是所有审查类机制的**共同前提**。没有对照物，两层审查（G4）和 UI/UX 两端覆盖（G5）都失去锚点，只能退化为印象判断。长链路转述的语义漂移是结构性问题，无法通过"让 Agent 更小心"解决。

**成本影响**：增加一次落盘动作与少量维护成本。收益是审查从此有据可依、争议可回溯、返工范围可界定——对个人开发者来说，这直接决定了"改了三版还是不对"这类消耗能否避免。

## 建议四：为 UI/UX 增设执行后的对照走查环节

**机制**：在执行后增加一次对照走查，明确由某个角色负责，以执行前定标为唯一评判依据，逐项核验并给出量化结论。走查不通过则退回修正，不进入结算。

**理由**：缺口 ② 造成视觉质量处于无人区——执行前有设计、执行后没人管，而评审岗明确排除视觉判断。这与 G5"两个端点"的要求相比缺了后半段。仅靠执行前定标无法保证落地质量，必须有对称的验收动作。

**成本影响**：增加一个固定环节。但因为对照物已经存在（建议三），走查是**逐项核对**而非重新判断，单次成本可控。相比视觉问题在交付后才暴露的返工代价，这是划算的。

## 建议五：把流程约束升级为强制状态推进，并支持回滚

**机制**：六步流程从文档描述升级为**强制状态机**——每步有明确的进入与退出条件，非法跃迁被拒绝；关键节点保存检查点，支持回滚到任意检查点与相邻快照对比。

**理由**：缺口 ④ 的本质是"流程可被善意绕过"。文档描述的流程在长链路执行中会被逐渐简化，而个人开发者恰恰最缺外部监督。状态机把"应该怎么做"变成"只能怎么做"，与 G6 的流程层、状态层要求一致。回滚能力则把试错成本从"重来"降到"退回"。

**成本影响**：初期需要把六步的判定条件想清楚，是一次性的设计投入。运行期会增加少量状态管理开销，但换来的是流程不可跳过、中断可恢复、变更可审计。对单人项目尤其重要——没有同事帮你记住上次做到哪。

## 建议六：明确人工关口的触发条件

**机制**：把 Human-in-the-loop 从"随时可介入"细化为**有明确触发条件的三个节点**：需求确认（任务下发前，澄清范围与边界）、中期抽查（长周期任务的固定间隔或风险信号触发）、最终验收（交付前，以对照物为基准）。

**理由**：现有的"人工闸门"存在但触发条件模糊。没有明确触发条件的人工关口在实际执行中会被跳过或无限后延，等于没有。明确条件后，人工介入从"凭感觉"变成"按规则"，也让个人开发者能预判自己何时必须停下来做判断。

**成本影响**：几乎无额外成本，只是把已有的闸门明确化。收益是减少"该停没停"导致的返工。
