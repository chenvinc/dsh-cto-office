cto-office v2.0 · 设计汇报（第二版）· 2026-11-25

先让越界必现，
再解锁并行

本版把主张收窄为一句可站住的话：写者不给自己出结论；验收的启动权仍在 CTO，但验收的证据来源与放行权在宿主与人。按此重排落地顺序：一期只做「可判定性」——单检出、写卡串行、每卡提交边界、授权清单、diff 判定； 二期才上 worktree 并行。核心主张（越界必现、纪律可判定、做的人不验收）一期就能兑现， 只有「并行」这一项推迟 —— 而它恰恰是最需要先拿真实数据说服人的部分。

基线 v0.2.4（7 预设 / 653 行 patch） 宿主 DSH 0.2.2-rc.5 一期 A 9–12 + B 5–6 · 二期 9–14（可能缩减） 唯一未定项 档位实测（见末节）

一页结论

v2.0 分两期做，两个期各回答一个问题：一期回答「结果能不能被判定」，二期回答「并行能不能被安全放开」。角色数量不变（仍是 1 + 6），权限不放宽，反而更紧。

1 个写者一期 `maxConcurrentWriters = 1`，串行写卡
1 个提交边界每卡 `baseSha`，改动可归因
1 个写入点工件只在主检出，worker 只读
0新增角色与放宽的权限
一句话记住 v2.0：一期的价值不是「更快」，是「错了能被发现」；二期的价值才是「更快」，而它建立在一期之上。

01为什么要改

现状不是「缺功能」，而是四个缺口与一个与核心主张正面冲突的风险。以下数字均来自代码审查。

架构骨架其实已经对了

  • 星型拓扑：六岗位 preset 都没有 subagent，信息只能经 CTO 中转
  • 单一 Orchestrator：拆解与把关同一个人
  • 未挂 subagent_fork / workflow：切断权限扩散路径
  • 只读岗真的没有写工具（配置层关闭）

所以 v2.0 不动拓扑、不动角色数 —— 只在骨架上补流程细节。

这轮改的是一个我自己犯的错

  • 第一版把最重的 worktree 隔离压在一期，而它恰好与三条未闭合的硬伤强耦合
  • 硬伤没闭合就上隔离，一期会交付「跑起来但不可判定」的系统
  • 重排后：一期证明「判定有效」，二期才证明「并行划算」

顺序换一下，风险就从「架构级返工」降到「范围调整」。

02岗位角色设计

七个预设、七份规程不变。变的是每个岗位「能被判定的产出」和「预算档位」。

岗位作用（一句话）解决的痛点不做什么
CTO把人的一句话拆成能判定的卡，派人、验货、汇报拆解与把关分家导致的信息损耗不写实现；写也要先说明并取得同意
架构师先把契约钉死，再让写者开工开工前没有共同事实，各写各的不写文件、不做实现、不拍视觉
工程师按卡实现，交自检证据与可归因的提交低级问题直扑深度审查不审自己的活、不改契约与验收标准
评审对着 diff 判「写对了吗」，给 PASS/CHANGES没有可对照物 → 只能印象判断不替人改代码、不做产品与视觉判断
QA对着验收基线逐条实测，给 PASS/FAIL「做对了吗」与「写对了吗」混为一谈不评风格、不接受「大部分通过」
UI/UX执行前定标（规格），执行后对照走查视觉质量在交付后落入无人区不落盘、不替用户定品牌调性
业务把模糊需求变成可测的验收标准需求不可测 → 验收无从谈起不排优先级、不评估技术可行性
设计取舍：不新增角色。UX 的执行后走查复用 cto-ux（它已有看图能力），评审与 QA 的「双闸」仍是两张并行只读卡。原因是 npm run check 里写死了「恰好 7 个 preset」，新增角色会同时触发 sync 断言、面板、文档三处返工。

03一期：可判定性

一期不建 worktree、不放开并行。它只回答一个问题：一张卡做得对不对、改得越没越界，能不能由机器判定。

M1 · 串行写卡 + 每卡提交边界

配置项 maxConcurrentWriters = 1：第二个写岗派工直接被 pre-execute 拒绝。开卡时把当时的 HEAD 冻成 baseSha，卡完成时必须已提交。

为什么一期串行

单检出下两个写者同时改，git status 分不清哪行是谁的，「每卡判定」当场失效。串行是最便宜的修复。

为什么二期不用改判定

二期只改两处：并发上限数值、baseSha 的取值来源（改为 baseCommit）。字段名与判定逻辑一律不动。

结算纪律

串行下脏工作区会传染：前一张卡的残留会被算进下一张卡。所以结算必须提交或清理，否则不许开下一张。

M2 · 授权清单 + 双读判定 + 互斥组

开卡时写死清单 { mode, include, deny, exclusive }；完成时 双读 git diff --name-status <baseSha>..HEAD 与 git status --porcelain，逐条 glob 匹配。

为什么要双读

  • diff --name-status 看不到未跟踪文件、删除、重命名
  • status --porcelain 看不到已提交的内容
  • 只读一条就会漏，两条合起来才是完整事实
  • 非 git 仓库回退到快照 hash；构建产物靠 .gitignore 兜住

互斥组 exclusive（修复共享文件双写）

  • 同一 glob 同时只能被一张在飞卡持有
  • 第二张卡在开卡时进入 blocked_by 排队，不进入并行
  • 冲突从「合并那一刻」提前到「开卡那一刻」暴露 —— 后者便宜得多
  • 典型场景：shared/types.ts、路由表
必须说清的边界：这是事后判定，不是事前阻止。阻止只有三层：工具不挂载（已做）、沙箱工作区边界（宿主级）、只读模式（逐会话可切）。所以话术是「越界必被发现」，不是「越界不可能」。

提权流：子代理返回 ESCALATE: {文件, 理由} → CTO 自决或转人 → 更新清单（CAS revision，留审计）→ 重跑判定。拒绝也给理由，理由写回卡，下一张卡不再犯同一个错。

M3 · 工件契约 + 回执闸门

这是第一版最大的漏洞：工件放在主检出，worker 却在独立检出里 —— worker 读不到对照物，回执还会被判越界。修法是把契约写死。

回执与自检的固定字段

RECEIPT:
- card: C1
- artifactsVersion: contracts=3, acceptance=2      ← 冻结所读版本
- changed: api/import.ts, app/import/page.tsx      ← 必须 ⊆ 授权清单
- acceptance:                                      ← 逐条判定，不许笼统
  - A1 PASS
  - A2 PASS 证据：pnpm test import → 12 passed
  - A3 FAIL 原因：>10 万行 CSV 未测
- selfRisk: 大文件内存占用未验证
SELF-CHECK:
- build: pnpm build → 0
- tests: pnpm test import → 12 passed
- scope: api/import.ts, app/import/page.tsx
- gaps: >10 万行 CSV 未压测
缺字段就打回，是 fail-closed —— 但这次是对的。因为回执是判定的输入，输入不齐没法判；这与「判定器自身校验失败不能 fail-closed」（见第 07 节）不矛盾。

证据怎么存：一件一文件，永不覆盖

  • 每条证据一个文件：evidence/<intentId>.json，写一次只读一次
  • 崩溃最坏结果是「新文件不存在」—— 不存在是安全状态（重跑该 intent 即可）；覆盖替换则可能毁掉已有的好数据
  • 只有 card.json 这类必须原地更新的汇总游标，才用「temp → fsync → rename → fsync 目录」五步
  • 读到 0 字节或 schema 不全 → 判 CORRUPT 并转人工，不许容错成空对象（空对象会被当成"无证据"，做出更坏的结论）

卡粒度硬上限（否则上面全部退化成形式）

维度上限执行点
变更文件数≤ 10开卡记声明值（排期预警）；
office_gate 硬拦
净变更行数≤ 400
可观测行为变化恰好 1 条（对应 1 条 acceptance）

为什么硬拦在 gate 不在 dispatch：开卡时预知不了实际改多少文件，"dispatch 拒绝建卡"实现不出来。一张巨型卡永远是"授权内"的 —— 没有这条上限，隔离与判定都没有意义。

04二期：解锁隔离

一期证明「判定有效」之后，二期才谈并行 —— 但先改名字：它买的是「隔离」，不是「更快」。三条外部证据同向否定「多写者同时改更快」，被支持的只有隔离价值。建不建 worktree 由一期数据决定。

二期可能缩减：若一期跑满指标后「排队阻塞率」不高，二期只做状态机 + 检查点 + 断点恢复，不建 worktree。判据见第 08 节的双门槛与决策表。
为什么不是一开始就上 worktree：外部证据（CooperBench：跨模块并行写使成功率从 50% 降到 25%）指向的是同目录并发写，不是并行本身。但「隔离后判定仍成立」这个前提必须先被验证 —— 一期就是在验证它。

M4 · 阶段机 + 四项检查点

M5 · UX 后置走查 + 人工关口

执行后走查（补上缺的后半段）

  • 依据只有一份：acceptance/<id>.md
  • 逐条核验，回执末行 GATE: WALK PASS n/m
  • 未过走查的卡不能结算
  • 在合并后的主检出做 —— 这是唯一出口，结论不随分支删除消失

三处人工关口（有触发条件）

  • 需求确认：澄清出口必须有一次用户确认
  • 中期抽查：回退达阈值、或即将触碰不可逆动作
  • 最终验收：结算前，以对照物为基准
  • 回退次数从"文档里的提醒"变成计数器

三类检查各在哪跑（必须写清，否则"通过"没有定义）

环节执行位置判据
office_gate检出无关（纯文本比对）diff/status vs 授权清单
SELF-CHECKworker 自己的检出内对 acceptance 逐条
UX 走查 / 终验合并后主检出唯一出口，settle 前置
一句话：越界判定与检出无关，行为验收只在合并后。

05一卡一流

把一个写任务从开卡到结算画成泳道：谁做什么、留下什么工件、卡在哪一关。一期形态（无 worktree、无 merge）。

060 → 1 全流程模拟

模拟项目：从零做一个「个人记账 Web 应用」的最小可用版 —— CSV 账单导入、自动分类、月度统计。六天，七个岗位各出场一次以上。

  1. D0 · 澄清：把一句话变成可测

    人给一句话：「想把我招商银行和中国银行的账单导进来，看看每月花多少。」CTO 判出三个歧义且有不可逆风险，一次问全：① 多币种要不要？② 原始 CSV 是否留存？③ 是否需要登录与多设备？

    产物：cards/decision-001/card.json（答案 + 为什么这么问）→ 业务岗据此出7 条可测验收标准（不许出现「友好」「流畅」）。

  2. D1 · 契约先行：让判定有对照物

    架构师交付四项：方案对比、契约（accounts / transactions / imports 三张表、导入 API 形状、错误语义）、拆卡建议、风险清单。UX 交付三屏规格，把空态/错误态/加载态定死。

    CTO 把契约与验收基线落盘，此时冻结 artifactsVersion，然后开两张写卡：C1 数据层 + 导入 API、C2 导入页 + 列表页，各自带授权清单与 baseSha。

  3. D2 · 串行实现：一次只有一个写者

    C1 先跑，只碰 db/** 与 api/**。C2 因为 maxConcurrentWriters=1 在队列里等 —— 这不是浪费，而是保证「这段改动是谁写的」永远没有歧义。

    中途一次提权：C2 发现需要改共享类型 → 返回 ESCALATE: shared/types.ts — 导入失败态需要新增 error code。CTO 判断合理，把该文件加进 C2 清单，理由与决定都落在卡上。注意：shared/types.ts 被登记进 exclusive 组，C1 已结算所以不冲突；若 C1 还在飞，C2 会继续排队 —— 冲突在开卡时就暴露，而不是在最后。

  4. D3 · 自检 → 闸门：低级问题不到评审面前

    两张卡交回时都带 RECEIPT + SELF-CHECK；C2 第一次漏了 gaps 行，被宿主自动打回，补齐后才进闸门。判定：C1 越界 0、C2 越界 0（提权后清单已覆盖），两卡文件数与行数都在粒度上限内。

    评审与 QA 是两张并行只读卡（只读不占写者名额）：评审判「写对了吗」→ GATE: PASS；QA 判「做对了吗」→ GATE: FAIL 5/7，两条失败都有最小复现：10 万行 CSV 超时、空文件报错不友好。

  5. D3 后半 · 回退一次，然后全绿

    回退只回到 C1，不推翻 C2；修完复跑 QA 7/7。回退计数器记 1（达 2 转人、第 3 次 deny，这次没到）。

    这一步体现「分层」的价值：如果评审先被格式与构建错误占满，就不会有精力抓出「超时」这种真问题。

  6. D4 · UX 后置走查：视觉不再落在无人区

    UX 对着同一份验收基线走查 4 条，3 条通过，1 条不通过：首屏空态没有引导。回退补空态后再走查 → GATE: WALK PASS 4/4。

    走查不是在评「好不好看」，而是逐条核对「规格里定的七个状态是否都实现了」—— 所以它便宜、可复跑、可争论。且它在合并后的主检出跑，结论不随分支消失。

  7. D5–6 · 结算、复盘

    每张卡结算时必须已提交（工作区除 .cto-office/ 外干净），否则不许开下一张。卡置完成 + 证据落盘 + 四行汇报（做完了什么 / 已知边界 / 工作区状态 / 风险与下一步）。

    复盘只改一样东西：把「gaps 行必填」写进卡模板，因为它是这次唯一被自动打回的原因。

    这里要纠正第一版的一个说法：第一版把「两人都动了路由表、合并时一次解决」写成机制有效的演示 —— 它其实是反证：授权清单本身不预防共享文件双写，只在你事后才发现，而且暴露在最贵的时刻。这一版的 exclusive 组就是为了把它提前。

07谁监管 CTO

前面所有隔离、判定、状态机都是给岗位和流程设的，而 CTO 正是流程的驱动者。所以必须单独回答：谁盯着盯着的人。

现有设计防不了这两种情况

机制对 CTO 的约束力缺口
工具边界无：root 挂全量工具，write/edit 都在「不自己下场」只是铁律，CTO 改代码是完全合规路径
派工弱：派谁、派几轮、派不派评审都由 CTO 定可以不派评审直接进结算
闸门证据无：GATE: 行写在回执文本里CTO 自己写一行 GATE: PASS，与真评审无法区分
状态机能拦住跳步拦不住「在被允许的阶段里伪造结论」
授权清单不适用：清单只约束 workerCTO 直接改主检出，diff 无从比对

两道补丁（已按批注降级，只留下真正有效的）

P1 · 闸门证据改由宿主提取 最关键

门禁不读文件里的文本，而是在 post-execute 时从子代理会话事件的末行解析 GATE:，并校验来源 preset 是评审或 QA。面板本来就这么做（client.js:348），把同一份解析搬到宿主即可。

拦住：CTO 伪造 PASS。为什么关键：它把闸门从"自述"变成"事实"，且不需要新能力。

P2 · CTO 写盘留痕 + 一次人确认

对 root 的写操作首次走一次授权（一次会话问一次，不是每次都问 —— 改十行弹十次没人受得了），之后每条在审计账本记 actor: cto。

拦住：CTO 悄悄改代码、悄悄改工件。

三个权力分开（核心主张的精确版本）

权力属于谁为什么
启动权（派不派、派几轮）CTO本来就不该被剥夺
出结论权评审 / QA（非写者）做的人不给自己出结论
放行权宿主来源校验 + 人CTO 既不能伪造、也不能跳过
于是核心主张收窄成一句能站住的话：写者不给自己出结论；验收的启动权仍在 CTO，但验收的证据来源与放行权在宿主与人。
原来的「验收独立于 CTO」站不住 —— 评审与 QA 都是 CTO 派的 preset，它决定派不派、派几轮。

刷闸门：CTO 反复派工直到某次 PASS

每次调用都合法、每次结论都真实，但结果是「用重试换通过」。处置不是直接拒绝（会误判测试抖动 —— diff 没变而测试转绿是合理情况），而是：

  • CHANGES 之后无代码变更就 PASS → 标 suspicious_pass，进每日看板「异常信号」栏，不阻塞，但不计入闸门通过率
  • rounds 计数器统一管回退与重试：≥2 转人、≥3 deny（不再单列"派遣上限"避免两套数字打架）

被我砍掉的两条（说明为什么）

原方案为什么砍保留了什么
append-only hash 链账本hash 链只在"写账本的人不能改账本"时有意义；插件跑在你机器上、仓库写权限也在你手里，有权限就能重算整条链 —— 链只防自己普通 audit.jsonl：插件写、CTO 只读、进 git 可 review。"能 review"比"能验 hash"实用
外部锚点 CI单人仓库里"本地测试撒谎"的受益者与受害者是同一人，没有对手就没有外部锚定动机合并门跑一次干净检出全量测试（临时 worktree + 依赖缓存，不重新 clone）—— 拿到"环境纯净度"这半价值，成本低一个数量级
还有一层必须诚实：被监管者能改监管者。当工作对象就是这个插件时，CTO 可以让工程师改掉判定逻辑，监管自我失效。这层只做到「不变则已，一变必响」：启动时校验自身文件 hash，不一致就告警 + 面板常亮（不阻塞判定），并在 CI/评审里可见。单人仓库里这防得住无意的漂移，防不住有意的绕过 —— 它是提醒机制，不是安全边界。
必须接受的部分：目标与范围（做不做、先做哪个）、判断质量（设计是否合理）不在机器监管范围内。所以监管的边界是过程可审计、结果可复算、目标由人定 —— 而不是给 CTO 配一个上级。

08怎么证明有效

不用「感觉更顺了」来验收。但要小心：单看一个指标必然误读，所以每条信号都必须成对读。

信号单独读会怎样配对指标判定
闸门一次通过率 ≈ 100%像是质量好变更分散度（每卡文件数分布）分散度高 → 判据太松或没人看；分散度正常 → 可能真的简单
回退次数恒为 0像是很顺卡粒度（文件数 / 行数）卡都很小 → 合理；卡很大且零回退 → 闸门没在拦
授权清单持续变宽像是需求变化提权理由分布集中于共享文件 → 该建 exclusive 组；分散 → 卡拆得不好
每卡 token 持续上升像是任务变难卡粒度 + 回退次数token 涨而粒度没涨 → 上下文在漏
工件版本长期不变像是稳定卡数量卡在涨而工件不涨 → 工件层没在落盘
走查记录高度雷同像是一致性好走查条数 vs acceptance 条数不相等 → 走查没逐条
「闸门 100% 通过」与「回退恒 0」必须当失败信号读，不能当质量指标。否则面板一上线就会被误读成「机制运行良好」—— 这是最容易犯、也最难自察的错。

二期开工判据：双门槛 + 决策表（不靠拍脑袋）

五类指标全部来自现有机制，不新增组件：卡时长分布、阻塞率、越界检出率、回退率、共享文件冲突数。

门槛要求为什么
样本量≥ 3 个独立工作周期 且 ≥ 15 张卡20 张卡的阻塞率中位数，置信区间宽到能装下任何结论；且一周内的卡常来自同一种任务形态
判据形态看趋势：连续 2 个周期超阈值才建议动工单点会骗人
样本不足面板只显示「数据不足」，不显示建议避免 5 张卡的中位数被当成结论
人工提前决策允许，但落 {decision:'early', sampleState:'insufficient', decidedBy:'human'}让「凭判断拍板」和「有数据支持」在审计里可区分
条件行动
阻塞率持续 > 40% 且 卡时长中位数 > 1 小时动工 worktree
阻塞率低但越界检出率高先修判定层，不上隔离
指标全低暂缓，worktree 可能不值得做
阻塞率中等 + 回退率高先优化任务拆分
故障注入会污染指标，必须隔离。9 个注入用例会产生 gate 打回、CHANGES、QUEUED 记录，直接把越界检出率和回退率抬高。1–7 在 scratch 工作区跑，8–9 在「一次性克隆的真实项目」里跑（跑完即删）—— 同时拿到端到端保真和零污染；sampleTag 挂 card 上作兜底。统计只取 real。

一期不验证什么（防止用一期数据替二期担保）

项一期二期
越界必现、自检有效、工件不漂移✅ 验证复用
并行收益（多写者是否更快）❌ 无样本✅ 唯一验证点
worktree 隔离是否真能防干扰❌✅
合并冲突处理❌ 一期没有 merge✅

二期不得引用一期数据当担保 —— 串行形态下不产出任何并行数据。

09落地路线

按 A/B 切分。每个组件只归一期，A 必须能独立交付并被断言。

一期 A · 可判定内核（9–12 人日）

工作包内容估算
W0六项兼容实测 + 声明修正 + 迭代回路 + 门禁 + 依赖清单1–2 天
W1串行写卡 + 授权清单 + baseSha 提交边界 + 双读判定 + exclusive + 防篡改3–4 天
W2工件单写入点 + artifactsVersion + RECEIPT/SELF-CHECK + 回执抓取3–4 天
W1c卡粒度硬上限 + rounds 计数器（回退与重试合并）0.7 天
W1dQUEUED 态 + abandoned/settled 终止态（含释放 exclusive）0.5 天
W1e超时监督器最小报警（15 分钟轮询，一句话推送）0.3 天
W1fevidence.json 仅记录（四类 source 落盘，不参与判定）0.5 天
A 阶段的 `GATE` 防伪只完成一半 —— 必须说清：
✅ 挡得住「直接写一行 GATE: PASS」：P1 只认子代理会话事件，文件里的文本不参与判定（P1 在 A，不在 B）。
❌ 挡不住「造一个空壳 preset 冒充评审」：CTO 改 patch 即可 —— 这道门在 B（改 preset 需人确认）。
⚠️ 部分挡「让真评审橡皮图章」：标 suspicious_pass + rounds 上限，但不阻塞。
A 交付后能断言的只有三条：越界必现、改动可归因、证据来源可区分。崩溃仍不可恢复，机制有效性仍未被证明 —— 那是 B 的事。

一期 B · 机制加固（4–6 人日）

工作包内容估算
W3判定事务（intentId + latest-wins + 持久化替换 fsync 五步）0.7 天
W4evidence.json 判定白名单生效（cto-narrative 不参与判定）0.5 天
W5故障注入 9 用例 + 脚本化 + 验收报告视图0.8 天
W6指标 + 3 周期 / 15 卡双门槛 + sampleTag 隔离1 天
W7三处宿主门槛（改 preset 需人确认 / 进行期禁改工件 / 锁 TTL）1 天
W8依赖清单 + platform-probe1 天
W9超时监督器完整版 + 每日看板完整版0.7 天

二期 · 解锁隔离（9–14 人日，可能缩减）

worktree 隔离（判定路径不改）→ 阶段机 + 检查点 + 回滚 → UX 走查 + 人工关口 → 岗位档位与成本（最后做）→ 面板与 0.3.0。若一期指标不支持，缩为「状态机 + 断点恢复」。

工期为什么涨了 60%

初版 8–11 人日只看 W0+W1+W2+回退计数器。14 条建议 + 6 补丁 + 3 收紧 + 2 漏洞，每一笔都是真机制，合计 14–18 人日。

涨幅本身就是「机制折损速度」的示范：把「半天搞定」按真实成本记账，比事后延期诚实。

三个停点（你随时可以停）

停点人日能断言
停点 0 · W13–4越界必现（最硬的一半）
停点 1 · 一期 A9–12+ 改动可归因、来源可区分
停点 2 · 一期 B5–6+ 崩溃可恢复、有效性可证

对一个还没跑过一行代码的框架，第一个可验证点不该在 12 天后 —— 这就是停点 0 的意义。

已知风险（如实写）

  • bash 写路径只能做到「规则级」兜底，不承诺内核级
  • 提交边界需配 reset/amend 拦截，否则攻击面变大
  • 并行对时间窗额度的挤占折算不出来，只能实测
  • 插件目录解析 @deepseek-ai/* 会落到 npx 缓存旧版（已实测：rc.1 vs 宿主 rc.5）→ 关键依赖自实现

明确不做（本期）

  • 不新增角色、不放宽任意岗位权限
  • 不换派工形态（仍用子代理）
  • 不引入社区 skill
  • 不按模型分档、不拉取外部点数
  • 不接 CI、不做 hash 链、不做自校验 fail-closed
